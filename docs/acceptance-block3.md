### Сессия живым пальцем

1 × `MULTITOUCH_ERROR`. Все строки `sessions.csv` и `trials.csv` несут
`schema_version = stage1-1.1.0` — в отличие от переэкспортированной сессии блока 2, где

### Миграция базы 1 → 2

Проверена в реальной постановке: на устройстве стоял release-APK блока 2 с данными, новый
release установлен поверх. Приложение стартовало, кнопка экспорта активна, сессия блока 2
экспортирована.

В её строке `sessions.csv` двенадцать колонок счётчиков **пусты**, а `schema_version` —
`stage1-1.0.0`. Оба факта верны: эти данные записаны сборкой, которая счётчиков не вела, и
подставлять нули означало бы заявить, что потерь не было, — а это неизвестно.

`fallbackToDestructiveMigration` намеренно не включён: упасть честнее, чем молча стереть
данные заказчика.

### Проверка критерия 29

Переполнение очереди и отказ записи сами по себе не случаются — за весь блок 2 ветка
обработки ошибок не исполнилась ни разу. Оба отказа вызваны намеренно, **временной
правкой, которая в поставку не вошла**.

Правка затрагивала только `TrialRepository.persist`. Весь остальной путь — счётчики и
коды ошибок библиотеки, липкая строка на экране, запись счётчиков в строку сессии,
сборка архива — исполнялся тем же кодом, что и в поставляемой сборке. Текст правки:

```kotlin
override fun persist(trial: TrialSnapshot): Boolean {
    // STALL: первый вызов держит worker, очередь на 64 слота переполняется тапами
    if (FAULT == "STALL" && !stalled) { stalled = true; Thread.sleep(12_000) }
    // FAIL: первые пять попыток не записываются
    if (FAULT == "FAIL" && failuresLeft > 0) { failuresLeft--; return false }
    return persistInternal(trial)
}
```

**29a, переполнение очереди.** 150 тапов за 13.8 с при заблокированном worker'е:
на экране «завершено 150 · подтверждено 85», строка ошибок — 65 переполнений, 0 отказов
записи, код 1 (`QUEUE_OVERFLOW`). В `sessions.csv` `trials_accepted = 85`,
`queue_overflows = 65`; в `trials.csv` 85 строк. Шестьдесят пять потерянных попыток
отсутствуют в архиве и объяснены счётчиком — §9.5 соблюдён на всём пути, а не только на
экране.

**29b, отказ записи.** 12 тапов, первые пять `persist` возвращают `false`: «завершено 12 ·
подтверждено 7», строка ошибок — 0 переполнений, 5 отказов, код 2 (`WRITE_FAILURE`). В
`sessions.csv` `trials_accepted = 12`, `trials_confirmed = 7`, `write_failures = 5`; в
`trials.csv` 7 строк.

**29c, поставляемый артефакт.** Правка откачена, `release` пересобран и установлен заново,
сценарий 100 TAP прогнан на нём: 100 · 100, счётчики нулевые. Иначе в поставку уехала бы
сборка, которую после последней правки не запускали.

Архивы обоих отказов лежат в `delivery/` — они и есть долговременное доказательство,
поскольку переживают удаление кода.

**Честное ограничение.** Критерий 29 проверен на временной сборке, а не на поставляемом
APK, — в отличие от критериев 25–27 и 30, проверенных на нём.

### Прочие проверки

- **Экспорт сессии с нулём попыток.** Архив собирается, CSV состоят из одних заголовков,
  ссылочная целостность не нарушена. Валидатор блока 5 должен это пережить.
- **Повторный экспорт.** Экспорт одной сессии дважды даёт файл с тем же именем и
  **побайтно совпадающим** содержимым; 100 попыток в базе на месте. §10.2 «успешный экспорт
  не удаляет внутренние данные» соблюдён. Имя архива детерминировано сессией, а не
  моментом экспорта, поэтому повторный экспорт перезаписывает файл, а не плодит копии.
- **Чистка каталога.** Тринадцать экспортов разных сессий: в `filesDir/exports` осталось 10.
- **`targetSdk` 36.** После правки границы области касания перемерены на устройстве:
  890 × 1187 px, ровно как в блоке 2. Инсеты не сдвинулись.
- **`lintRelease`.** Появилось `OldTargetApi` — «targetSdk не самый новый». Это прямое
  следствие уточнения №11, требующего `targetSdk = 36`, а не недосмотр; подавлять
  замечание не стали, чтобы расхождение с `compileSdk` оставалось видимым. Остальные
  замечания прежние: версии AGP и Gradle, `LockedOrientationActivity` (портрет зафиксирован
  намеренно), `DrawAllocation`, `DiscouragedApi`. Ошибок нет.
- **`docs/sample/last-trial.json`** пересобран живым пальцем на схеме `stage1-1.1.0`:
  свайп со статусом `UP`, 21 текущий отсчёт и 31 historical.
  `docs/measure_touch_rate.py` даёт 202.7 Гц по потоку `MotionEvent` при 90 Гц обновления
  экрана — очередная иллюстрация к критерию 22. Полей в JSON попытки не добавилось: все
  двенадцать счётчиков живут на уровне сессии, в `sessions.csv`.
  Дамп снят отдельным коротким проходом из трёх свайпов, а не основной сессией: он пишется
  по последней завершённой попытке, а последней в основной сессии был мультитач, который
  `measure_touch_rate.py` намеренно пропускает.

## Как устроена запись счётчиков

```
finishSession ──> CLOSING ──> collector.endSession()   [блокирует до фиксации всех попыток]
                                      │ барьер сомкнут
                     Diagnostics(now) ─┴─ Diagnostics(baseline при startSession)
                                      │ разность = «за эту сессию»
                     closeSession(ended_at, COMPLETED, counters)  ── одна транзакция
```

Снимок раньше барьера занизил бы `trials_confirmed` без всякой ошибки: часть попыток ещё
не дошла бы до `persist()`. Разность с базой нужна потому, что `Diagnostics` копит за всё
время жизни коллектора, а коллектор переживает и экран, и предыдущие сессии.
