# Отчёт по блоку 2 — Приложение

Этап 1, блок «Приложение» (§3.2, §5.1, §9.3, §12) вместе с перенесённой вперёд частью
блока хранения. Дата прогона: 01.09.2026.
Версия схемы данных: `stage1-1.0.0`, версия библиотеки: `1.1.0`, версия приложения: `1.1`.

## Устройство проверки

| | |
|---|---|
| Модель | Samsung SM-A525F (Galaxy A52) |
| Android | 14, API 34 |
| Экран | 1080 × 2400, 90 Гц, density 420 |
| Область касания | 890 × 1187 px после применения инсетов |

Прогон: 8 сессий, 138 попыток. Из них 119 синтетическим вводом (сценарии целостности) и
19 живым пальцем — сессия `p-finger`, включая мультитач и 14 свайпов для замера частоты.

Синтетический ввод для частоты и сырых каналов непригоден в принципе: `adb shell input`
идёт через `InputManager.injectInputEvent` мимо тач-контроллера, не порождает второго
пальца и отдаёт `touch_major = 0`, `pressure` 0/1. Всё, что касается частоты, каналов и
мультитача, измерено живым пальцем.

## Что изменилось по сравнению с блоком 1

`:app` перестал быть хостом-заглушкой. Раньше он держал коллектор внутри Activity,
не имел слоя хранения и показывал «подтверждено N из N», не записав ни байта.

| Было | Стало |
|---|---|
| Коллектор создаётся в `onCreate`, убивается в `onDestroy` | `SessionController` внутри `SessionViewModel`, переживает пересоздание экрана |
| Приёмник не установлен, `confirmedTrials` растёт сам | Room-приёмник, `persist()` возвращает `true` только после коммита транзакции |
| Идентификаторы `t-1`, `cs-1`, `dp-1`, обрезанный `session_id` | UUID во всех четырёх идентификаторах |
| `onResume` обновляет только сессионную точку синхронизации | попытка перевооружается: новая точка применяется до первого касания |
| Техсводка без min/max каналов, разбор JSON поиском подстроки | все величины §12, считаются из `TrialSnapshot` за один проход |
| Ошибки схлопнуты в одно число | липкая строка ошибок: переполнения, отказы записи, код и текст |
| `keepScreenOn` включён всегда | `FLAG_KEEP_SCREEN_ON` только на время активной сессии |
| Отступ области касания — фиксированные 24 dp | максимум из базового, зоны системных жестов и выреза |
| Экспорта нет | CSV × 6 + `schema.json` + `README.md` → ZIP → FileProvider → «Поделиться» |
| Аварийный рестарт не отслеживается | сессия, оставшаяся `ACTIVE`, помечается `INCOMPLETE` на холодном старте |
| `last-trial.json` пишется из callback-а на пути фиксации | диагностический дамп под флагом, по умолчанию выключен |

## Результаты прогона

### Сессия `p-finger`: живой палец, 19 попыток, 877 отсчётов

| Величина | Значение |
|---|---|
| Статусы завершения | 18 × `UP`, 1 × `MULTITOUCH_ERROR` |
| Отсчётов | 877, из них historical 553 |
| Частота отсчётов в потоке MotionEvent | **≈255 Гц** — 14 свайпов, 759 отсчётов за 2978 мс |
| `1/median(Δt)` | 253 Гц |
| Δt между соседними отсчётами | min 0.87 · median 3.95 · max 37.45 мс |

Замер согласуется с блоком 1 (≈259 Гц на том же аппарате); разница объясняется более
короткими свайпами: 150–190 мс против 0.5–1.1 с. Отношение 255 Гц к 90 Гц — прямая
иллюстрация к критерию 22: частота обновления дисплея и частота отсчётов касания
разные величины.

Образец `docs/sample/last-trial.json` пересобран из этой сессии (попытка 19), поэтому
`docs/measure_touch_rate.py` работает на актуальной схеме с UUID.

### Сырые каналы за сессию

| Канал | Мин | Макс | Различных значений |
|---|---|---|---|
| `touch_major` | 0.425 | 5.947 | 13 |
| `touch_minor` | 0.425 | 5.522 | 12 |
| `size` | 0.004 | 0.051 | 22 |
| `pressure` | 1.000 | 1.000 | **1** |
| `orientation` | 0.000 | 0.000 | 1 |

`pressure` на этом устройстве постоянен — как и в блоке 1. Значение сохранено как есть и
ничем не подменено: критерий 33.

### Проверки экспортированного архива

На архиве сессии `p-finger` (`delivery/session-p-finger-20260901.zip`) проверены и
выполнены:

- ссылочная целостность пяти идентификаторов — `participant_id`, `session_id`,
  `trial_id`, `display_profile_id`, `clock_sync_id`;
- порядок событий внутри каждой попытки: первый отсчёт `ACTION_DOWN`, последний
  соответствует статусу завершения;
- нестрогое неубывание времени события во всех попытках;
- время historical sample не превышает времени родительского события;
- `common_timestamp_ns = touch_event_time_uptime_ns + offset_ns` на каждом отсчёте;
- `history_index` заполнен у historical и пуст у текущих отсчётов;
- `relative_time_ms` первого отсчёта равен нулю;
- сходимость `current_sample_count + historical_sample_count` с фактическим числом строк;
- `MULTITOUCH_ERROR`: `ACTION_POINTER_DOWN` последним, `action_index` и `pointer_count`
  сохранены;
- `timestamp_precision = NANOSECONDS` и `app_receipt_uptime_precision = MILLISECONDS` на
  всех отсчётах — верно для API 34, где `getEventTimeNanos()` уже есть, а
  `SystemClock.uptimeNanos()` ещё нет.

Те же проверки выполнены на архиве синтетической сессии из 102 попыток.

## Дефекты, найденные прогоном

Три штуки, все исправлены и перепроверены на устройстве.

### 1. Безопасный отступ не применялся вовсе

Слушатель `OnApplyWindowInsetsListener` не вызывался ни разу: без edge-to-edge decor
поглощает инсеты до нашего корня. Область касания прилегала к краям на 32 px — это
padding разметки, — вместо расчётных 63 px, а зона жестов навигации снизу не
учитывалась совсем.

Разбором кода это не ловилось: код выглядел правильным, и только измерение границ
области на устройстве показало 32 вместо 63.

Исправлено: `WindowCompat.setDecorFitsSystemWindows(window, false)`, отступ корня
складывается с базовым, а не заменяет его. После правки нижний отступ — 126 px, ровно
зона жестов навигации; боковые — 63 px.

### 2. Счётчик считал за всё время жизни коллектора, а не за сессию

Коллектор теперь переживает и экран, и предыдущие сессии, а `Diagnostics` копит
сквозняком. Во второй сессии после 50 тапов на экране было 100. §12 требует счётчик
попыток, а попытки принадлежат сессии.

Исправлено: `SessionController` снимает базу счётчиков в `startSession` и вычитает её.

### 3. Область касания сдвигалась после первой попытки

Техсводка вырастает с одной строки до пяти, и мишень уезжала вниз на 34 px посреди
сессии. Для инструмента сбора касаний это существенно: распределения точек касания
между попыткой 1 и последующими становятся несравнимыми.

Исправлено: шапка получила фиксированную высоту со скроллом, область касания больше не
зависит от длины текста. Проверено: границы области совпадают до первой попытки и после
третьей.

## Как это устроено

### Состояние сессии

```
IDLE ──startSession──> ACTIVE ──finishSession──> CLOSING ──барьер сомкнут──> CLOSED
                          ^                                                    │
                          └──────────────── startSession ──────────────────────┘
```

Состояние — поле `SessionController`, а не набор флагов у кнопок. Начать сессию из
CLOSING нельзя по построению: раньше это держалось на том, что обе кнопки вовремя
выключили.

Контроллер живёт в `SessionViewModel`. Область видимости выбрана намеренно: ViewModel
переживает пересоздание Activity (смена темы, размера шрифта, опция «не сохранять
активности») и уничтожается, когда экран завершён по-настоящему, — то есть даёт честное
место для `shutdown()`. У объекта в Application такого места нет: `Application.onTerminate`
на устройстве не вызывается.

Смерть процесса ViewModel не переживает, поэтому она дополняется пометкой незавершённой
сессии, а не заменяет её.

### Порядок записи и подтверждение

```
onTouchEvent ─> SessionController.processTouch ─> RawTouchCollector (главный поток)
                                                        │ offer в очередь
                                          worker коллектора
                                                        │
                              TrialRepository.persist ──┴─> транзакция Room
                                                              │ коммит
                                          true ───────────────┘
```

`persist()` возвращает `true` только после коммита. Это единственный источник счётчика
«подтверждённо сохранённых»: §9.5 запрещает показывать попытку сохранённой без
подтверждения, а до появления приёмника библиотека считала подтверждённым всё подряд —
строка `target?.persist(snapshot) ?: true` при отсутствии приёмника.

Строка сессии пишется идемпотентно из двух мест: сразу после старта на потоке хранилища,
чтобы она появилась даже если попыток не будет, и внутри транзакции каждой попытки,
чтобы порядок был гарантирован, а не вероятен. Вставить её на главном потоке нельзя —
Room это запрещает; отдать в фон и забыть тоже нельзя — первая попытка может дойти до
записи раньше.

### Гарантия перед экспортом

`finishSession` переводит автомат в CLOSING и уходит на отдельный поток, потому что
`endSession()` блокируется до подтверждения фиксации всех принятых попыток. Область
касания перестаёт принимать события в тот же момент, поэтому §9.4 «новые касания не
должны незаметно попадать в формируемый архив» выполняется по построению, а не по
удачному стечению обстоятельств. Кнопка экспорта активна только в CLOSED.

### Незавершённая сессия

Отдельного маркера в `SharedPreferences` нет: маркером служит сама строка сессии со
статусом `ACTIVE`. Одна сущность вместо двух, которые могли бы разойтись.

На холодном старте, до того как оператор сможет начать новую сессию, все строки со
статусом `ACTIVE` переводятся в `INCOMPLETE`. `ended_at_wall_clock_ms` остаётся `null`:
календарное время завершения такой сессии неизвестно, и подставлять текущее было бы
враньём. Продолжить такую сессию нельзя — только начать новую с новым `session_id`.
Число восстановленных сессий показывается оператору.

### Состав архива

| Файл | Содержимое |
|---|---|
| `devices.csv` | производитель, модель, Android, sdk_int, версии приложения и AAR, density_dpi |
| `display_profiles.csv` | профили, на которые ссылаются попытки сессии |
| `sessions.csv` | сессия, включая `session_status` и сессионный `clock_sync_id` |
| `clock_sync.csv` | все точки синхронизации сессии |
| `trials.csv` | завершённые попытки |
| `touch_samples.csv` | отсчёты; historical sample — отдельная строка |
| `schema.json` | версия схемы, состав файлов, смысл идентификаторов |
| `README.md` | краткое описание для получателя архива |

Имена колонок берутся из `SchemaFields` — того же объекта, что и в JSON попытки. Ради
этого он стал публичной частью API библиотеки: вторая копия имён неизбежно разошлась бы
с первой.

Пустая ячейка означает `null`, то есть «неприменимо». Так пишутся `history_index` у
текущего отсчёта и `ended_at_wall_clock_ms` у незавершённой сессии.

`timestamp_precision`, `app_receipt_uptime_precision` и `clock_sync_id` постоянны внутри
попытки, поэтому в базе лежат один раз, в строке попытки, а в `touch_samples.csv`
печатаются в каждой строке — как того требует состав полей §6.4.
