# Отчёт о технической проверке — RawTouchCollector

Этап 1, блок «AAR-библиотека». Дата проверки: 27.08.2026, замер частоты отсчётов касания — 29.08.2026.
Версия библиотеки на момент прогона: `1.0.0`, версия схемы данных: `stage1-1.0.0`.

## Устройство проверки

| | |
|---|---|
| Модель | Samsung SM-A525F (Galaxy A52) |
| Android | 14, API 34 |
| Экран | 1080 × 2400, 90 Гц |
| Частота отсчётов касания | **≈259 Гц** в потоке MotionEvent (измерено живым пальцем, см. ниже) |

API 34 — показательный случай: наносекундное время события уже доступно (`MotionEvent.getEventTimeNanos()`, с API 34), а наносекундный uptime ещё нет (`SystemClock.uptimeNanos()`, с API 35). Обе ветки точности работают одновременно и видны в данных.

### Мультитач, требование §8

Проверено трижды, вручную, двумя пальцами. Все проверки пройдены во всех прогонах:

| Проверка | Результат |
|---|---|
| Статус попытки `MULTITOUCH_ERROR` | ✓ |
| `ACTION_POINTER_DOWN` сохранён **последним** отсчётом | ✓ |
| `action_index` сохранён | `1` |
| `pointer_count` сохранён | `2` |
| `second_pointer_observed` | `true` |
| Первый отсчёт — `ACTION_DOWN` | ✓ |
| `POINTER_DOWN` встречается ровно один раз | ✓ |
| После `POINTER_DOWN` ничего не записано | ✓ |
| Время события не убывает | ✓ |
| `trial_index` без пропусков | 1, 2, 3 |

Хвост записи прерванной попытки:

```
 …
 103  MOVE      hist=False ptrId=0 actIdx=0 ptrCnt=1
 104  MOVE      hist=True  ptrId=0 actIdx=0 ptrCnt=1
 105  MOVE      hist=False ptrId=0 actIdx=0 ptrCnt=1
 106  PTR_DOWN  hist=False ptrId=0 actIdx=1 ptrCnt=2   ← последний отсчёт
```

События прерванного жеста, пришедшие после этого момента (31 штука в итоговой сессии), отброшены согласно §8 п. 4 и учтены отдельным счётчиком `eventsDiscardedAfterMultitouch` — это штатное поведение, а не отклонение.

Замер 29.08.2026: живой палец, 11 свайпов подряд внутри области попытки, длительность

Считает `docs/measure_touch_rate.py`; на приложенном образце (`t-13`) он даёт 264.2 Гц:

```
python docs/measure_touch_rate.py 'docs/sample/*.json'
```

Основная оценка получена как отношение числа отсчётов к суммарной длительности контакта,
то есть устойчива к разной длине свайпов; `1/median(Δt)` приведена рядом как контрольная.

**Что именно измерено.** Это частота отсчётов в потоке `MotionEvent`, доставленном
приложению, а **не** паспортная частота опроса тач-контроллера. Между сенсором и приложением
стоят драйвер и `InputReader`, которые вправе объединять отсчёты, поэтому измеренное значение
является нижней оценкой частоты отчётов драйвера. Паспортную частоту панели по этим данным
получить нельзя: для неё нужен либо datasheet, либо чтение `/dev/input/eventX` в обход
`InputReader`.

Синтетический ввод для такого замера непригоден в принципе: `adb shell input` инжектит события
через `InputManager.injectInputEvent`, минуя тач-контроллер и его драйвер, а `input tap` не
порождает ни одного `ACTION_MOVE`. Полученная так «частота» характеризует скорость инжекции,
а не сенсор. Все значения этого раздела измерены живым пальцем.

**Структура потока.** Распределение Δt трёхмодальное (кластеры ≈1.5, ≈3.8 и ≈5.8 мс) — это не
шум, а батчинг: `Choreographer` отдаёт пакет раз в кадр дисплея (11.15 мс), внутри пакета лежат
3 отсчёта с повторяющимся паттерном интервалов ≈5.8 / 1.5 / 3.9 мс. Отношение 259 Гц к 90 Гц —
почти ровно 3 отсчёта на кадр, что и является прямой иллюстрацией к критерию 22: частота
обновления экрана и частота отсчётов касания — разные величины, и вторая здесь втрое выше.

### Синхронизация временных шкал

| Параметр | Значение |
|---|---|
| Метод | `MS_BOUNDARY` |
| Погрешность выборки | 521–950 нс |
| Погрешность квантования | **0** |
| Откатов на `MS_PLAIN` | 0 из 102 |

Рецепт из п. 7.3 ТЗ (сохранять как погрешность ширину интервала между двумя чтениями `elapsedRealtimeNanos`) не учитывает, что `uptimeMillis()` квантован до миллисекунды: неизвестная дробная часть до 1 000 000 нс целиком уходит в смещение. Заявленная погрешность оказалась бы занижена примерно в тысячу раз.

По согласованию с заказчиком реализовано другое решение:

1. Погрешность разложена на два независимых слагаемых — `sync_sampling_uncertainty_ns` и `sync_quantization_uncertainty_ns`, — потому что по одному суммарному числу нельзя понять, измерение было неточным или шкала грубой.
2. Квантование снимается измерением: спин-цикл ловит момент перещёлкивания `uptimeMillis()`, в который истинное uptime заведомо равно целому числу миллисекунд. Активное ожидание до 1 мс приходится на момент перед попыткой, когда палец экрана не касается.
3. Если момент упущен из-за вытеснения потока, происходит откат на обычное чтение с честным `quantization = 1 000 000` и пометкой `sync_method = MS_PLAIN`.

На этом устройстве приём работает на всех точках синхронизации: квантование снято полностью.

### Проверка выгруженных данных

На образце `docs/sample/last-trial.json` (попытка `t-13`, живой палец, 241 отсчёт за 908 мс) проверены 14 инвариантов, все выполнены:

порядок событий; монотонность `sample_index`; нестрогое неубывание времени события и `common_timestamp_ns`; время historical sample не превышает время родительского события; `relative_time_ms` первого отсчёта равен нулю; `history_index` заполнен у historical и `null` у текущих; единый `clock_sync_id` внутри попытки; сходимость счётчиков отсчётов с фактом; равенство `common = uptime + offset` для каждого отсчёта; согласованность `quantization = 0` с методом синхронизации.

## Как воспроизвести проверку

1. Собрать и установить: `gradlew.bat :app:assembleRelease`, затем `adb install -r -t app/build/outputs/apk/release/app-release.apk`
2. Запустить приложение, нажать «Начать сессию»
3. Выполнить нужный сценарий в зелёной области
4. Нажать «Завершить сессию»
5. Счётчики — на экране; полная диагностика и JSON последней попытки — в logcat по тегу `TouchLab`
6. Данные попыток: `/sdcard/Android/data/com.lime.touchlab/files/`

### Повторить замер частоты отсчётов

`last-trial.json` перезаписывается каждой попыткой, поэтому файлы надо забирать по ходу:

1. Отключить повышенную чувствительность экрана и энергосбережение, зафиксировать их состояние
2. Начать сессию и сделать 10–12 свайпов внутри зелёной области, **живым пальцем**, по 0.5–1.0 с
   каждый, не отрывая палец и не останавливая движение: на неподвижном пальце контроллер
   не обязан выдавать новые отсчёты, и частота будет занижена
3. После каждой попытки забирать файл:
   `adb exec-out cat /sdcard/Android/data/com.lime.touchlab/files/last-trial.json > trial-NN.json`
4. `python docs/measure_touch_rate.py 'trial-*.json'`

Синтетический ввод (`adb shell input`) для этого замера непригоден: он минует тач-контроллер,
а `input tap` вообще не порождает `ACTION_MOVE`.
