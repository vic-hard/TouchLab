# Отчёт о технической проверке — RawTouchCollector

Этап 1, блок «AAR-библиотека». Дата проверки: 27.08.2026.
Версия библиотеки: `1.0.0`, версия схемы данных: `stage1-1.0.0`.

## Устройство проверки

| | |
|---|---|
| Модель | Samsung SM-A525F (Galaxy A52) |
| Android | 14, API 34 |
| Экран | 1080 × 2400, 90 Гц |
| Частота отсчётов касания | **226 Гц** (измерено) |

API 34 — показательный случай: наносекундное время события уже доступно (`MotionEvent.getEventTimeNanos()`, с API 34), а наносекундный uptime ещё нет (`SystemClock.uptimeNanos()`, с API 35). Обе ветки точности работают одновременно и видны в данных.

## Критерии приёмки, относящиеся к библиотеке

| № | Критерий | Статус | Чем подтверждено |
|---|---|---|---|
| 11 | AAR не зависит от Activity, публичный API Java-совместим | **выполнен** | `ApiCompatCheck.java` компилируется, вызывая каждый публичный метод; конструктор принимает `Context`, не `Activity` |
| 14 | Записываются DOWN, MOVE, UP, CANCEL, POINTER_DOWN и все historical samples | **выполнен** | касание пальцем: 24 отсчёта, из них 14 historical; свайп 310 мс: 29 текущих + 27 historical |
| 15 | MotionEvent не передаётся на отложенную обработку | **выполнен** | поля копируются в примитивные массивы внутри `processMotionEvent`; в очередь уходит неизменяемый снимок |
| 16 | Все поля раздела 6 в документированной схеме либо явно помечены | **выполнен** | `docs/schema-stage1.md`; недоступные поля пишутся явным `null` (`history_index` у текущих отсчётов) |
| 17 | `participant_id` в данных сессии и однозначно связан с попытками | **выполнен** | поле присутствует в каждой попытке; см. образец |
| 18 | Календарное время отдельно от uptime/elapsedRealtime | **выполнен** | `started_at_wall_clock_ms` / `ended_at_wall_clock_ms` из `System.currentTimeMillis()`, ни одно uptime-поле так не называется |
| 19 | На API 34+ nanos-методы; ниже — MILLISECONDS | **выполнен на API 34**, ветка 31–33 не проверена | `timestamp_precision = NANOSECONDS`; у живого пальца **24 отсчёта из 24** имеют ненулевую дробную часть миллисекунды |
| 20 | Обе receipt-метки, точность uptime-метки явно обозначена | **выполнен** | `app_receipt_time_uptime_ns` + `app_receipt_time_elapsed_ns`; `app_receipt_uptime_precision = MILLISECONDS` (uptimeNanos нет на API 34) |
| 21 | Для каждой попытки применимая clock_sync; после onResume — новая | **выполнен** | точка снимается в `startSession`, в каждом `startTrial` и по `invalidateClockSync` из `onResume` |

| 23 | Мультитач: POINTER_DOWN сохранён, статус MULTITOUCH_ERROR, trial_id не продолжается | **выполнен** | три прогона двумя пальцами, все 10 проверок пройдены (ниже) |
| 24 | Сериализация и запись не выполняются синхронно в главном потоке | **выполнен** | `JsonWriter` и `TrialSink.persist()` вызываются только на worker-потоке |
| 25 | Не менее 100 последовательных TAP без потери | **выполнен** | `accepted=100 confirmed=100`, все счётчики ошибок нулевые |
| 28 | Быстрое завершение сессии A и старт B не смешивают данные | **выполнен** | по 50 TAP в каждой: `{s-b504dda3=50, s-eacac472=50}` |
| 29 | Переполнение очереди и ошибки записи фиксируются явно | **выполнен** | 150 TAP против приёмника с задержкой 200 мс: `accepted=128`, `queueOverflows=22`, сумма ровно 150 |
| 33 | Постоянный канал не считается ошибкой при честном сохранении | **выполнен** | `pressure` на этом устройстве константа 1.0, сохраняется как есть; `size`, `touch_major`, `touch_minor` меняются |

## Результаты прогонов

### Целостность данных

| Сценарий | Результат |
|---|---|
| 100 последовательных TAP | `accepted=100 confirmed=100`, ошибок 0 |
| TAP → немедленный `endSession` | `accepted=102 confirmed=102 pending=0` |
| Сессия A → сразу сессия B, по 50 TAP | `{A=50, B=50}`, смешивания нет |
| 150 TAP против приёмника 200 мс | `accepted=128 + queueOverflows=22 = 150`, потерь без учёта нет |
| Итоговая сессия (тап, мультитач, тап) | `accepted=3 confirmed=3 pending=0 beforeStart=0 discardedAfterMultitouch=31 multitouch=1`, прочие счётчики 0 |

### Мультитач, требование §8

Проверено трижды, вручную, двумя пальцами. Все проверки пройдены во всех прогонах:

| Проверка | Результат |
|---|---|
| Статус попытки `MULTITOUCH_ERROR` | ✓ |
| `ACTION_POINTER_DOWN` сохранён **последним** отсчётом | ✓ |
| `action_index` сохранён | `1` |
| `pointer_count` сохранён | `2` |
| `second_pointer_observed` | `true` |
| Первый отсчёт — `ACTION_DOWN` | ✓ |
| `POINTER_DOWN` встречается ровно один раз | ✓ |
| После `POINTER_DOWN` ничего не записано | ✓ |
| Время события не убывает | ✓ |
| `trial_index` без пропусков | 1, 2, 3 |

Хвост записи прерванной попытки:

```
 …
 103  MOVE      hist=False ptrId=0 actIdx=0 ptrCnt=1
 104  MOVE      hist=True  ptrId=0 actIdx=0 ptrCnt=1
 105  MOVE      hist=False ptrId=0 actIdx=0 ptrCnt=1
 106  PTR_DOWN  hist=False ptrId=0 actIdx=1 ptrCnt=2   ← последний отсчёт
```

События прерванного жеста, пришедшие после этого момента (31 штука в итоговой сессии), отброшены согласно §8 п. 4 и учтены отдельным счётчиком `eventsDiscardedAfterMultitouch` — это штатное поведение, а не отклонение.

### Синхронизация временных шкал

| Параметр | Значение |
|---|---|
| Метод | `MS_BOUNDARY` |
| Погрешность выборки | 521–950 нс |
| Погрешность квантования | **0** |
| Откатов на `MS_PLAIN` | 0 из 102 |

Рецепт из п. 7.3 ТЗ (сохранять как погрешность ширину интервала между двумя чтениями `elapsedRealtimeNanos`) не учитывает, что `uptimeMillis()` квантован до миллисекунды: неизвестная дробная часть до 1 000 000 нс целиком уходит в смещение. Заявленная погрешность оказалась бы занижена примерно в тысячу раз.

По согласованию с заказчиком реализовано другое решение:

1. Погрешность разложена на два независимых слагаемых — `sync_sampling_uncertainty_ns` и `sync_quantization_uncertainty_ns`, — потому что по одному суммарному числу нельзя понять, измерение было неточным или шкала грубой.
2. Квантование снимается измерением: спин-цикл ловит момент перещёлкивания `uptimeMillis()`, в который истинное uptime заведомо равно целому числу миллисекунд. Активное ожидание до 1 мс приходится на момент перед попыткой, когда палец экрана не касается.
3. Если момент упущен из-за вытеснения потока, происходит откат на обычное чтение с честным `quantization = 1 000 000` и пометкой `sync_method = MS_PLAIN`.

На этом устройстве приём работает на всех точках синхронизации: квантование снято полностью.

### Проверка выгруженных данных

На образце `docs/sample/last-trial.json` проверены 14 инвариантов, все выполнены:

порядок событий; монотонность `sample_index`; нестрогое неубывание времени события и `common_timestamp_ns`; время historical sample не превышает время родительского события; `relative_time_ms` первого отсчёта равен нулю; `history_index` заполнен у historical и `null` у текущих; единый `clock_sync_id` внутри попытки; сходимость счётчиков отсчётов с фактом; равенство `common = uptime + offset` для каждого отсчёта; согласованность `quantization = 0` с методом синхронизации.

## Как воспроизвести проверку

1. Собрать и установить: `gradlew.bat :app:assembleRelease`, затем `adb install -r -t app/build/outputs/apk/release/app-release.apk`
2. Запустить приложение, нажать «Начать сессию»
3. Выполнить нужный сценарий в зелёной области
4. Нажать «Завершить сессию»
5. Счётчики — на экране; полная диагностика и JSON последней попытки — в logcat по тегу `TouchLab`
6. Данные попыток: `/sdcard/Android/data/com.lime.touchlab/files/`
